# Curated destinations dataset — source notes (BS-029)

**Artifact:** `data/curated_destinations.csv`
**Assembled:** 2026-08-26
**Rows:** 30 European cities
**Schema:** `city,country,country_code,lat,lon`

- `country_code` — ISO 3166-1 alpha-2 (uppercase). This is the join key to
  `fuel_prices.country_code` (see `docs/schema.sql`) and to per-country data.
- `lat` / `lon` — decimal degrees (WGS84), city-centre reference point. These
  map to `destinations.latitude` / `destinations.longitude` on ingest.

## Purpose

This is the **raw ingestion source** for ScoutAgent's curated PostgreSQL
destination dataset (technical documentation §8, §19). It is deliberately a
*controlled domain dataset*, not mock data: a normalized table of real
destinations assembled from open sources. No scoring or feature engineering is
done here — that happens downstream (BS-030 loads these rows into the
`destinations` table; `destination_features` is populated separately, enriched
by WhereNext cost-of-living data per §8.1).

## Selection criteria

Target: 20–40 European cities that are **realistic budget destinations from a
Central/Eastern-European origin** (the thesis's worked examples — Budapest,
Prague, Belgrade, Thessaloniki — imply a Balkan/CEE home origin such as Sofia).
The list therefore leans toward Central Europe, the Balkans, the Baltics, and
affordable Southern-European cities, with a few pricier anchors (Vienna,
Lisbon) kept for contrast so Scout's budget pre-filter has range to work with.

## Sources

Every row is drawn from open, redistributable references:

1. **City / country names & ISO 3166-1 alpha-2 codes** —
   [ISO 3166 country codes](https://www.iso.org/obp/ui/#search) (the alpha-2
   standard; also mirrored in the public-domain
   [`datasets/country-codes`](https://github.com/datasets/country-codes) list).
2. **Coordinates (lat/lon)** — city-centre points from
   [GeoNames](https://www.geonames.org/) (CC BY 4.0), cross-checked against
   [OpenStreetMap / Nominatim](https://www.openstreetmap.org/) (ODbL). Rounded
   to 4 decimal places (~11 m precision), which is ample for coarse
   transport-distance estimates.

Both coordinate sources are open-licence and citable for the thesis; no
scraped, proprietary, or EULA-restricted data (e.g. Numbeo) is used here.

New rows can also be added by city name with `scripts.add_destination`, which
resolves country, ISO code and coordinates via the **Open-Meteo geocoding API**
(free, no key, **CC BY 4.0**) — the same open-data provider used for the seasonal
normals.

## Notes / caveats

- `Czechia` is used as the country name (ISO short name) rather than the older
  "Czech Republic".
- Istanbul (`TR`) straddles Europe/Asia; included as a realistic budget
  destination reachable overland from the origin. Its centre point is on the
  European side.
- Coordinates are single city-centre reference points, not bounding boxes;
  per-POI and per-accommodation coordinates come from the specialist agents
  downstream, not from this file.

## Related datasets (BS-031 feature engineering)

- `data/destination_features_raw.csv` — per-destination factor counts
  (culture/nature/nightlife/food/tourism) + climate class. The five factor
  columns are **generated from OpenStreetMap** by `scripts.ingest_osm_features`,
  not hand-authored.
- `data/osm_features_raw.json` — **committed snapshot of OpenStreetMap POI
  counts** per destination (Overpass API, 12 km radius). **Attribution (required
  by ODbL):** "© OpenStreetMap contributors, licensed under the ODbL 1.0." No API
  key required.
- `data/season_profiles.json` — **committed snapshot of per-city seasonal
  suitability** derived from Open-Meteo climate normals (archive/ERA5,
  2014–2023), generated by `scripts.ingest_season_normals`. **Attribution
  (required by CC BY 4.0):** "Weather data by Open-Meteo.com." No API key
  required.
- `data/wherenext_cost_of_living.json` — **committed snapshot of WhereNext
  cost-of-living data** (getwherenext.com, `GET /api/data/cost-of-living`), used
  as the offline/CI fallback for cost-of-living ingestion (BS-011). **Attribution
  (required by CC BY 4.0):** "Cost-of-living data © WhereNext (getwherenext.com),
  licensed under CC BY 4.0." The snapshot's `meta` block records the source,
  licence, and version. Full methodology: `data/FEATURES_METHODOLOGY.md`.

# Fuel prices — source notes (BS-032)

**Artifacts (committed snapshots / offline floor):**
- `data/fuel_prices_oil_bulletin.txt` — the fuel-prices.eu `llms-full.txt`
  machine-readable export (EU Weekly Oil Bulletin republished, CC BY 4.0).
- `data/fuel_prices_live_summary.json` — the fuel-prices.eu `/live/` station
  summary (`/live/api.php?action=summary`), used for non-EU neighbours.

**Snapshot captured:** 2026-08-29 (bulletin data date 2026-08-24).
**Target table:** `fuel_prices` (keyed by `country_code`; petrol_e95, diesel,
source, price_date).

## Sources

1. **EU-27 prices** — the authoritative, citable source is the **EU Weekly Oil
   Bulletin** (European Commission, DG ENER), ingested in practice from
   [fuel-prices.eu](https://www.fuel-prices.eu/) which republishes it as
   CC BY 4.0. Parsed from the "CURRENT FUEL PRICES — ALL COUNTRIES" table of the
   `llms-full.txt` export (Euro-95 + diesel, EUR/L, tax-inclusive).
2. **Non-EU neighbours** (MK, RS, BA, ME, TR) and any EU member the bulletin
   omits in a given week (e.g. GR) — **real** station-averaged prices from the
   fuel-prices.eu `/live/` summary feed (station open-data, ~12–18 h fresh).
   Labelled `source = "fuel-prices.eu live (station avg)"` with their own
   `price_date`, because the methodology differs from the EC weekly bulletin.
3. **EU-average fallback** — a country covered by neither source (currently only
   **AL**) is stored with the EU-27 average petrol/diesel, and a synthetic `EU`
   row holds that average as the ultimate fallback for any origin without a
   per-country price (`source = "EU Weekly Oil Bulletin (EU avg)"`).

## Attribution

fuel-prices.eu — data from the European Commission Weekly Oil Bulletin
(CC BY 4.0). Cite the EU Weekly Oil Bulletin as the authoritative source.

## Reproduce / refresh

Idempotent ingestion + refresh routine (upserts on `country_code`; a re-run
refreshes in place, never duplicates). From `backend/`:

```bash
python -m scripts.ingest_fuel_prices                  # live fetch + upsert
python -m scripts.ingest_fuel_prices --source snapshot # offline (committed data/)
python -m scripts.ingest_fuel_prices --dry-run         # resolve + report, no writes
python -m scripts.ingest_fuel_prices --save-snapshot   # refresh the snapshots above
```

Parsing + resolver + idempotency are covered by
`backend/tests/test_ingest_fuel_prices.py` (unit tests run with no database; the
idempotent-refresh test is an `integration` test that runs against Postgres).

## Automated weekly refresh

The Docker Compose stack runs the refresh on a schedule via an `ofelia`
scheduler service (`docker-compose.yml`): every **Friday 06:00 UTC** — safely
after the EU Oil Bulletin's Thursday (post-15:00 EET) update — ofelia execs
`python -m scripts.ingest_fuel_prices` inside the running `backend` container.
Because the ingest is idempotent, a missed or repeated run only refreshes rows
in place; no manual weekly entry is needed. Start it with the rest of the stack:

```bash
docker compose up -d          # brings up db, backend, scheduler, frontend
docker compose logs -f scheduler   # watch scheduled fuel-refresh runs
```

To change the cadence, edit the `ofelia.job-exec.fuel-refresh.schedule` label on
the `backend` service (6-field cron: `sec min hour dom mon dow`).

## Adding a new source (e.g. USA / Asia)

Fuel sources are pluggable. Storing a new region needs **no schema change** —
`fuel_prices` is keyed by ISO alpha-2 `country_code`, so `US`, `JP`, etc. fit as
they are. Ingesting one means writing a small provider that implements the
`FuelPriceProvider` contract in `backend/scripts/fuel_prices.py`:

```python
class UsEiaProvider:
    name = "us-eia"                 # shows up in provenance
    source_label = "US EIA"         # written to fuel_prices.source
    emit_all = True                 # ingest every country it returns
    def load(self) -> ProviderResult:
        prices = {"US": FuelDatum(petrol, diesel, price_date)}  # from the real feed
        return ProviderResult(prices, loaded_from="live")
```

Then resolve with it in the mix (priority = list order; first provider to supply
a country wins):

```python
from scripts.fuel_prices import resolve_from_providers, default_providers
records = resolve_from_providers(
    [*default_providers(), UsEiaProvider()],
    targets=("US", "JP", ...),
    # EU average is Euro-centric; pass a regional fallback or None for non-EU.
)
```

`emit_all=True` means "ingest everything this provider returns" (an authoritative
regional core, like the EU bulletin); `emit_all=False` means "only use it to fill
requested `targets`" (a supplementary feed, like the /live/ station data). The
resolver, ingest CLI, and `fuel_prices` schema stay untouched. See the worked
examples in `backend/tests/test_ingest_fuel_prices.py`
(`test_custom_provider_plugs_in_and_emits_its_countries`).

# Inside Airbnb raw listings — source notes (BS-033)

**Target table:** `airbnb_listings_raw` (raw staging; full CSV row as JSONB +
`snapshot_label`, `city`, `snapshot_date`, `listing_id`).
**Downloaded snapshots:** `data/inside_airbnb/<city>-<date>-listings.csv.gz`
(git-ignored — Inside Airbnb CSVs are tens of MB each and are never committed).

## Source & coverage

[Inside Airbnb](https://insideairbnb.com/get-the-data/) publishes quarterly
`listings.csv.gz` snapshots per city (the BS-007 primary accommodation source:
free, no key/account, **CC BY 4.0** with CC0 on the data). The importer resolves
the latest snapshot for each target city from the public index and downloads it.

Of the 30 curated destinations, **11 are covered by Inside Airbnb** (verified
2026-08-29): Athens, Budapest, Istanbul, Lisbon, Naples, Porto, Prague, Riga,
Thessaloniki, Valencia, Vienna. The Balkan/CEE cities (Sofia, Belgrade, Skopje,
…) are **not** published by Inside Airbnb and are handled downstream as
`estimated` (BS-007 decision; BS-034/035), not here.

## What is stored

This is a **raw** import: every row is stored verbatim (all ~90 columns preserved
in the `raw` JSONB), *before* any cleaning — including rows with an empty `price`
(e.g. 322 of Riga's 3,471). BS-034 validates and normalizes the usable rows into
`accommodations` (strip `$`/commas, prefer `price_quote_price_per_night` + its
currency, normalize to EUR, treat sentinel `999` nights as null). Keeping the raw
layer means those lossy steps can be re-run and audited without re-downloading.

`snapshot_label` = `inside-airbnb-<city>-<date>` records the exact snapshot;
`(snapshot_label, listing_id)` is unique so a re-run is an idempotent upsert and a
newer snapshot is added alongside (history preserved).

## Attribution

Inside Airbnb (insideairbnb.com), CC BY 4.0.

## Reproduce / re-run

Idempotent, chunked import. From `backend/`:

```bash
python -m scripts.ingest_airbnb                     # all covered target cities
python -m scripts.ingest_airbnb --cities riga,athens
python -m scripts.ingest_airbnb --dry-run           # download + count, no writes
python -m scripts.ingest_airbnb --limit 500         # cap rows/city (smoke test)
```

Row counts vs source and column presence are covered by
`backend/tests/test_ingest_airbnb.py` (unit tests use a small committed real
excerpt, `backend/tests/fixtures/airbnb_sample_listings.csv`; the
populate/idempotency test is an `integration` test that runs against Postgres).
